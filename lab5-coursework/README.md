# Порядок выполнения лабораторной работы 5

## 1. Перейдите в папку лабораторной работы
```sh
cd lab5-coursework
```

## 2. Создайте свою ветку
```sh
git checkout -b student-{ваш_номер}-lab5
```

## 3. Сдача работы

Лабораторная работа открывает курсовой проект, поэтому выполняется в **собственном публичном репозитории** на GitHub. В репозитории заданий сдаётся только ссылка на пул-реквест курсовой работы.

1. Создайте новый открытый репозиторий на GitHub `{project-name}` (название может отличаться, но должно отражать суть работы).
2. В репозитории создайте ветку `lab5` и выполняйте работу в ней. Ветка `main` должна быть пустой, но допускается первичный коммит с базовым `README.md`.
3. Создайте пул-реквест с ветки `lab5` на ветку `main`.
4. В репозитории заданий `js_6310_labs_2026` в ветке `student-{ваш_номер}-lab5` создайте файл `solutions/student-{ваш_номер}/solution.md` со ссылкой на пул-реквест курсовой работы:
```sh
mkdir -p solutions/student-{ваш_номер}
```
```md
# Лабораторная работа 5

Ссылка на пул-реквест курсовой работы: {ссылка}
```
5. Закоммитьте и запушьте изменения, создайте пул-реквест с ветки `student-{ваш_номер}-lab5` в ветку `main`:
```sh
git add solutions/student-{ваш_номер}/solution.md
git commit -m "Lab 5 solution by student {номер}"
git push origin student-{ваш_номер}-lab5
```

## 4. Задание

Тема курсовой работы выдаётся преподавателем. Работа состоит из двух частей: проектирование курсового приложения и реализация его каркаса. Обе части выполняются в одном репозитории курсовой работы.

### 4.1. Архитектурные и функциональные требования

Создайте в корне репозитория курсовой работы два файла.

#### `architecture.md` — архитектурные требования

- Опишите структуру проекта. Проект должен содержать **более одного проекта**: минимум основное приложение и библиотеку общих компонентов. Для каждого проекта укажите назначение, структуру папок и файлов.
- Приведите список используемых библиотек с версиями и назначением. Допускается использование UI-библиотек (base-ui, material-ui и аналогов).
- Опишите список разрабатываемых компонентов в рамках каждого проекта и их назначение.
- Определите структуру роутинга: маршруты, страницы, вложенность, страницы с параметрами и защищённые маршруты (если предусмотрены).
- Опишите, как основное приложение использует библиотеку общих компонентов.

#### `mvp.md` — функциональные требования к MVP

- Опишите минимум **один use case**, раскрывающий основной функционал приложения: актор, предусловия, основной сценарий, результат, альтернативные сценарии (если есть).
- Определите границы MVP: что войдёт в первую версию, а что останется за её пределами.

### 4.2. Каркас приложения

1. Создайте проекты, описанные в `architecture.md`, установите необходимые библиотеки.
2. Реализуйте структуру роутинга, страниц и компонентов.
3. Каждая страница и компонент могут не иметь полноценной реализации — допускается текстовая заглушка с описанием того, что страница или компонент будут отображать.
4. Все маршруты, страницы и компоненты из `architecture.md` должны присутствовать в проекте. Основное приложение должно запускаться, навигация между страницами должна работать без ошибок в консоли.
5. Библиотека общих компонентов должна реально использоваться основным приложением: как минимум один её компонент должен быть импортирован и отображён на странице.

### Дополнительные базовые требования

- Тип проекта должен быть `module`, использовать импорты и экспорты ES6. Ключевые слова `require`, `module.exports` — запрещены в исходном коде приложений (конфигурационные файлы jest и eslint могут быть на JS).
- `package.json` обоих проектов должен содержать команды `lint` и `lint:fix` в соответствии с примером.
- `package.json` обоих проектов должен содержать команды `test` и `test:coverage` в соответствии с примером.
- Язык разработки — TypeScript. Допускаются конфигурационные файлы jest и eslint на JS.
- Папка с решением (репозиторий с решением) должна содержать только необходимые файлы. Папки `coverage`, `node_modules` должны быть проигнорированы.
- Скрипты запуска `build`, `dev`, `lint`, `test` обоих проектов должны проходить без ошибок.
- В корне репозитория должны находиться файлы `architecture.md`, `mvp.md` и `README.md`.

### Нефункциональные требования

- `eslint` должен быть настроен с требованиями не ниже требований примера, с отступами в виде 2 пробелов, запретом на лишние переносы строк и знаки `;`. Команда `npm run lint` должна проходить без вывода предупреждений и ошибок.
- Все написанные тесты должны проходить.
- Все переменные и функции должны быть типизированы, использование ключевого слова `any` — не разрешается.
- Для библиотеки общих компонентов должны быть написаны юнит-тесты. Coverage хотя бы одного компонента библиотеки — не ниже 70% по всем столбцам.
- `README.md` должен содержать описание проекта, инструкцию по запуску, скрины с примерами работы приложения.
